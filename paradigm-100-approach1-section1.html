Proposed Design — Permanent Defense Layer (Section 1 of Approach 1)

What it must guarantee

  • No generator or contract module can ever cause a Vite import-analysis failure in the browser, even if it contains top-level or dynamic fs/path/child_process etc.
  • Dynamic loads from Studio preview code, engine-dispatcher fallbacks, or any future "live generator" feature must never pull Node-only code into the client bundle.
  • The protection must be automatic and hard to accidentally bypass.

Concrete Changes (all in the existing hardened config + one small addition)

1. Keep + slightly strengthen the existing plugin (already in your folder): - The resolveId hook already virtualizes anything under contracts/domains or *-contract for client. - Extend it to also catch any import whose id contains "/generators/" + a file that is known to have had Node side-effects in the past (or simply treat the entire generators/ tree as "client must only get pure functions"). 2. Add one small, robust transform that is impossible to miss: - Any dynamic import string that looks like a generator (contains "generators/" and ends with .ts or .js) gets an automatic /* @vite-ignore */ if it doesn't already have one. - This is defense-in-depth on top of the existing patterns. 3. (Optional but recommended for B + long-term) Add a tiny Vite dev-only plugin that, when running in "webview mode" (detected via env or query param), serves a "lite" shell with better preload hints for the critical Studio chunks.

How this directly enables A + C

With this layer in place, even if someone later removes a @vite-ignore comment by accident, or adds a brand new generator with top-level fs code, the client bundle will never see the bad import. The virtualization + auto-rewrite makes A (zero console errors on generator loads) and C (gates staying green) extremely robust.
