### 1.2 Genetic Operations – An Evolved Language

We define a **full genetic operation language** with these primitives:

- **`breed(parentA: Seed, parentB: Seed) -> childSeed`**  
  Crosses two seeds of possibly different or same domains. Implements multi-domain inheritance: if domains differ, produce a composed seed referencing both. Internally does gene-level crossover (exchanging compatible genes, mixing vectors). Handles `nexus` genes by merging references.

- **`mutate(seed: Seed, genesToMutate: string[], rng: RNG) -> Seed`**  
  Randomly mutates specified genes using the seeded RNG. Supports hierarchical mutation: if a gene is of type `recursive` or `graph`, it recurses into the structure.

- **`compose(seeds: Seed[], compositionGraph: CompositionSeed) -> Seed`**  
  Takes multiple seeds and composes them according to a visual composition graph (a seed which describes nodes and edges). Outputs a new seed representing the composed artifact. The composition graph itself is a new seed type with its own domain `CompositionGraph`.

- **`splice(seedA: Seed, seedB: Seed, genePaths: string[]) -> [Seed, Seed]`**  
  Swaps segments of genomes along specified gene paths. For example, splicing two `FullGame` seeds along a `morphic.playerCharacter` gene swaps protagonists between games.

- **`hybridize(seedA: Seed, seedB: Seed) -> Seed`**  
  A softer merge: blends gene values (e.g., averages numeric genes, mixes categorical distributions) rather than discrete crossover. Useful for smooth interpolation between designs (e.g., blending two color palettes).

- **`inject(seed: Seed, geneSet: GeneSet) -> Seed`**  
  Injects new genes (or overrides existing ones) into a seed, creating a child with added traits. For example, inject a `cybernetic` gene into a `Character` seed to add a robotic limb gene.

- **`evolveUntil(population: Seed[], fitnessFn: (seed: Seed)=>number, threshold: number, maxGens: number) -> {seed: Seed, history: LineageGraph}`**  
  Runs a genetic algorithm until a seed reaches a fitness threshold or maximum generations. The fitness function can be any computable metric (e.g., image novelty score). Returns the champion seed and full lineage graph.

- **`gradientAscent(seed: Seed, paramPath: string, stepSize: number, fitnessFn: (seed)=>number) -> Seed`**  
  Performs a numeric gradient search on a specific numeric gene (or vector), tweaking values to maximize the fitness function. Useful for fine-tuning parameters in domains like `Shader` or `Physics`.

- **`crossoverByIllumination(seedA: Seed, seedB: Seed, illuminationMap: Image) -> Seed`**  
  A novel operation where an image (e.g., a mask or exposure map) directs how two seeds' genes combine, pixelwise. In `Visual2D`, bright areas favor genes from A, dark areas from B.

- **`prune(seed: Seed, criteria: (geneName)=>boolean) -> Seed`**  
  Removes genes (sets them to defaults) based on a filter. This can strip unnecessary complexity (e.g., pruning unused `meme` genes from a `SocialNetwork`).

- **`differentiate(seed: Seed, dimension: string, amount: number) -> Seed`**  
  Focuses variation along one dimension/gene. For instance, in `Material`, differentiating texture granularity by 10% while keeping others constant.

Fitness functions become first-class citizens. Examples:

```yaml
fitnessFunctions:
  - name: aestheticScore
    type: ai-model
    model: StableDiffusionDetrendedCosine
  - name: structuralIntegrity
    type: simulation
    domain: Architecture
    ruleset: BuildingRegulations2025
  - name: marketPotential
    type: external
    api: BinanceSentiment
```

Clients can define custom fitness functions (e.g. via WebAssembly or cloud LLM APIs), enabling *AI‑driven evolution*. The `evolveUntil` operation can accept either static criteria or a real‑time metric from an external service.

### 1.3 Lineage as a Temporal Graph Database

We upgrade lineage tracking into a **full-fledged temporal graph**:

- **Branching Histories:** Each seed’s ancestry is a DAG, not just a chain. Seeds record all parents for multi-seed operations (breed, compose). The lineage database supports queries like “find all descendants with gene X mutated.”

- **Parallel Universes & Checkpoints:** We introduce named branches. A user can “fork” the evolution process, branching lineage to explore variations. Seeds carry branch labels. Example:  
  ```
  Seed A (v1) -> [evolve] -> Seed B (fitness=0.8) 
                           -> [fork->develop] -> Seed B_dev (v2_dev)
                           -> [fork->experiment] -> Seed B_exp (v2_exp)
  ```
  The lineage DB is a versioned graph, storing these branches and enabling rollback or merging branches later.

- **Causal Set Queries:** The graph database (implemented via a purpose-built in-memory store or a graph DB like Neo4j) supports complex queries:
  - *Example Query:* “List all seeds that inherited gene `characterTraits.hairColor` from seed `S` and later mutated it to red after 3 generations.”  
    This uses the temporal graph to trace gene propagation and transformation.

- **Lineage Visualization:** Beyond graphs, we store metadata for visualizing lineage trees with metrics on edges (e.g., “Fitness increased by +0.15”, “Cropping happened”). This makes the “Lineage Graph” UI richly informative.

- **Immutable Backups:** Because determinism is guaranteed, the entire lineage and seed store can be checkpointed to content-addressed storage (IPFS or Git) at any point. This provides snapshot-based recovery and trustable history.

### 1.4 Determinism & Reproducibility

Paradigm’s core promise is bitwise determinism:

- **Seed Hash Standard (RFC-PARADIGM-SEED):** We formally define the canonical JSON serialization for seeds (sorted keys, fixed float precision). Seeds’ SHA-256 hashes (with ECDSA-SHA256 signing) become unique identifiers. This is published as an open RFC.
  
- **RNG Contract:** The xoshiro256** algorithm with a specific seeding protocol is fully documented. An external library (with FFI bindings in Python/Go/Java) ensures cross-language reproducibility. RNG seeding uses a 256-bit seed derived from the seed’s content and parent lineage, guaranteeing same output globally.

- **Cross‑Language Implementations:** We provide reference implementations of the core kernel in at least three languages (TypeScript/Node, Rust, Python). Tests assert that any seed passed through the generator yields identical bytes. This makes Paradigm seeds portable.

- **Formal Verification (Optional):** For ultimate assurance, consider an SMT or Coq model of the RNG and core operations, proving that no floating‑point nondeterminism sneaks in. At minimum, the spec forbids using any non-deterministic APIs (no `Date.now()` in core logic, etc.).

- **Repro Execution:** Seeds can be “replayed.” For example, given a seed `S` and an operation log (mutation choices, breeding with partner IDs), any user can reconstruct the exact child seed. We embed sufficient metadata (RNG jump counts) to allow restarting an evolution at any generation step and produce identical intermediate populations.

*(In summary, Paradigm’s kernel ensures that “what you see is what you save.” This determinism is the foundation of trust, provenance, and collaborative creation.)*

### 2.3 Inter-Domain Composition Engine

We introduce a **node-based Composition Graph Editor** (in the Studio UI) where each node represents a domain generator or a transformation:

- **Graph Protocol as Seed:** A composition graph itself is a special seed of domain `CompositionGraph`. It contains nodes (with pointers to other seeds) and edges with functions. E.g., Node A (Character), Node B (Visual2D style), Edge f = “renderCharacterInStyle” yields Node C.  
  - *Spec:*  
    ```json
    {
      "domain": "CompositionGraph",
      "nodes": [
        {"id": "N1", "type": "input", "seedId": "seed-abc123"},
        {"id": "N2", "type": "transform", "function": "ApplyLighting", "params": {"intensity": 0.8}},
        {"id": "N3", "type": "output"}
      ],
      "edges": [
        {"from": "N1", "to": "N2"},
        {"from": "N2", "to": "N3"}
      ]
    }
    ```
  - The kernel can “run” this graph, feeding output of one node into the next. Complex graphs allow multi-stage pipelines (e.g., generate shape → extrude mesh → apply texture → set in scene).

- **Visual Editor:** Drag-and-drop interface in React for non-programmers. Supports sub-graphs (reusable modules) and allows for branching (run one seed through multiple transforms concurrently).

- **Recursive Composition:** Composition graphs themselves can include nodes whose operations spawn new seeds (like evolve loops), enabling meta-evolution. For instance, a node “FilterByAesthetic” could internally run an evolution process as part of one edge.

- **Versionable Graphs:** Composition graphs are versioned seeds. Users can “evolve” entire pipelines: mutate the graph itself (add/remove nodes, tweak parameters) and breed graphs (swap sub-graphs), generating novel generation workflows.

## 3. **The Operating System Metaphor – Fully Realized**

### 3.1 Paradigm Shell (PSH)

A command-line interface (`psh`) provides full access to core operations:

- **Commands:**  
  - `psh create --domain Music --name "EpicOrchestra" [--genes {...}]`  
  - `psh grow seed-123 --outFile theme.mid`  
  - `psh breed seed-123 seed-456 --mode hybrid --outName "Fusion"`  
  - `psh evolve population.json --fitness aestheticScore --target 0.95`  
  - `psh extract-graph lineage-abc --format svg`  

- **Script Files (.pscript):** Users write batch scripts for complex flows. For example:
  ```bash
  #!/usr/bin/psh
  # Compose a cinematic sequence
  create domain=Character name="Hero"
  create domain=Animation name="DanceMove"
  breed Hero DanceMove --outName "HeroDance"
  grow HeroDance --output "hero_dance.fbx"
  ```
  The `psh` shell supports loops, conditionals, and piping (e.g., piping seed JSON between commands). It integrates with standard shells (scripts can call `psh` commands).

- **Auto-completion & Manuals:** Built-in help, `man paradigm`, tab-completion for domains, genes, commands.

- **Interactive REPL Mode:** For quick queries and experimentation. E.g., entering `mutate seed-789` interactively shows effects.

### 3.2 Paradigm File System (PFS)

A virtual file system view of Paradigm data:

- **Mount Points:** Seeds, lineages, and populations appear as files/directories. For instance, `/pfs/seeds/seed-123.json` is the JSON seed, `/pfs/lineages/seed-123/graph.gexf` is its graph.
  
- **.pseed Executables:** A `.pseed` file is an executable seed. Double-clicking or “running” it (via OS) triggers the `grow` action, exporting the artifact. Internally, `.pseed` is a ZIP with the seed JSON plus metadata:
  ```
  mywidget.pseed/
    seed.json
    metadata.json (signature, lineage hash)
    preview.png
  ```
  The OS opens it with the Paradigm runtime to render outputs.

- **Mounting Remote Seeds:** PFS supports mounting seeds stored on IPFS or Arweave. Users can `cd` into `pfs/ipfs/<hash>/` to browse its structure (like a Git repo checkout).

- **Versioned Folders:** `/pfs/branches/develop/seed-ABC` shows a branch-specific view. `/pfs/tags/v1.0/` snapshots the state at releases.

### 3.3 Process Scheduler & Daemons

Background engines to manage long-running tasks:

- **Paradigm Daemon (`pshd`):** A service that queues tasks (evolutions, batch grows). It reads a JSON job spec:
  ```json
  { "jobType": "evolution", "population": "pop-001.json", "generations": 10000, "fitness": "marketPotential" }
  ```
  and runs in background, optionally reporting progress to a dashboard or via WebSockets.

- **Population Farm Manager:** For large-scale runs, support distributed computing. `pshd` can dispatch sub-tasks (e.g., simulate a set of individuals on different cores/machines) and aggregate results deterministically. It respects resource limits (configurable CPU/GPU caps).

- **Cron-like Scheduling:** Users can schedule periodic jobs, e.g. daily “create 10 new landscapes with sunrise lighting.” The scheduler ensures reproducibility by logging seeds and times.

- **Health Monitor:** `pshd` also monitors system health (disk space, memory) and alerts on issues. Logs are structured (JSON) for easy parsing.

### 3.4 Networking & Distributed Kernel

Paradigm becomes a **peer-to-peer network** of creative nodes:

- **P2P Protocol:** We design a network layer (based on libp2p/WebRTC) for exchanging seeds and updates. Peers can:
  - Publish a new seed to the network (like a pub-sub event).
  - Subscribe to streams (e.g., get seeds with a given tag).
  - Share portions of the lineage graph (for collaborative projects).

- **Federated Evolution:** Multiple instances can jointly evolve a population. For example, Node A and B both run `evolveUntil` on the same population, but share elite seeds via the P2P link, speeding convergence.

- **Consensus for Shared States:** If seeds are to be globally acknowledged (e.g. in an open marketplace), peers can vote or verify a seed’s signature, establishing trust without a central server.

- **Kernel Distribution:** The core API can run as a lightweight service on any device (even IoT or mobile). Seeds and code are JS/TS or WASM for cross-platform.

### 3.5 Security & Permissions

A fine-grained security model:

- **WebAuthn & DIDs:** Users register identities via WebAuthn (key pairs). Each seed’s `sovereignty` gene holds the creator’s DID (decentralized identifier). The system verifies signatures via DID Public Key Infrastructure.

- **Gene-Level Licensing:** Creator can lock certain genes. For instance, setting a `sovereignty` gene rule like `{protectedGenes: ["facialFeatures"], license: "CC-BY-NC", generations: 5}`. Any mutation operation checks these rules and enforces (e.g., forbidding change to protected genes or issuing warnings).

- **Permissioned Collaboration:** Seeds or populations can be shared with teams/groups. An ACL can be embedded as a special gene (`groupPermissions`) listing addresses with read/write/evolve privileges.

- **Encrypted Seeds:** Seeds containing sensitive data (e.g., trade secrets in Circuit designs) can be encrypted at rest. Only collaborators with keys (managed via WebAuthn) can decrypt. Signed seeds still verify, but payload is encrypted.

- **Audit Trail:** All operations (who mutated what and when) are logged immutably. The audit log is part of the lineage DB and is signed by the server’s key to prevent tampering.

*(This security model ensures that creators maintain full control over their intellectual property while enabling trustless collaboration.)*

## 4. **Decentralized Economy & Royalty Ecosystem**

### 4.1 Seed Asset Standard – S-Tokens

We define the **S‑Token (Seed Token)** standard to represent seed ownership:

- **On-Chain Anchoring (Optional):** Although Paradigm remains off-chain by default, users can mint an S‑Token for any seed on a blockchain of choice (Ethereum, Solana, etc.). The S‑Token holds the hash of the seed and its lineage. Metadata includes an Arweave/IPFS link to the full content.
  
- **Token Properties:**
  - `tokenId`: Unique on blockchain.  
  - `seedHash`: SHA-256 hash of seed.  
  - `author`: Creator DID.  
  - `license`: Encoded license info from seed’s sovereignty gene.  
  - `ancestors`: Array of parent tokenIds (for multi-parent seeds).  
  - `royaltyScheme`: URI or on-chain reference to a royalty distribution contract.

- **Off-Chain Ownership:** Even without minting, the system tracks “virtual S‑Tokens” by signature. Ownership transfers are recorded in a shared database or via a lightweight P2P ledger.

- **Fractional & Derivative Tokens:** We allow fractional ownership (like splitting royalties) and “derivative tokens” that reference parent tokens. E.g., if `SeedA` is a source material and `SeedB = breed(SeedA, SeedC)`, an “N‑Token” can represent a fraction of `SeedA` embedded in `SeedB`.

### 4.2 Royalty Engine

Automated royalty splits on creative output:

- **Royalty Graph:** Each time a grown artifact is sold/licensed (or printed on-demand), the royalty engine traverses its seed’s ancestry. Contributors are paid according to a configurable formula:
  ```yaml
  royalties:
    method: "exponentialDecay"
    baseRate: 0.10   # 10% of sale price is royalty pool
    decayFactor: 0.5 # Each generation gets half of previous
  ```
  If a seed has two parents, they split the parent-level share equally (or weighted by contribution percentages).

- **Configurable Distributions:** Options include:
  - *Linear:* Equal share per generation.
  - *Exponential:* Diminishing returns for distant ancestors.
  - *Custom:* Developers can define their own curves or flat fees.

- **Automated Payments:** For on-chain sales, smart contracts route payments per the scheme. Off-chain (e.g., in a built-in marketplace), the system issues invoices or directs built-in wallet transfers to parent addresses.

- **License Enforcement:** At runtime, the digital artifacts can embed license checks (e.g., a 3D model includes a DRM query to verify usage rights), ensuring royalties on unauthorized use. For example, an image seed exported as a PNG could embed a PayID link to the royalty contract.

### 4.3 Protocol Economy & Staking

Building a creator-driven economy:

- **Curation Markets:** Users can stake tokens (e.g., the platform’s native token or Ethereum) on promising seeds/populations. If a stake-holder’s chosen seed spawns a high-value derivative, they earn rewards. This is akin to a prediction market or crowd funding for good seeds.

- **Futures & Options:** Contracts can be written where, e.g., "20% of future royalties from SeedX are sold upfront for 10 Paradigm coins". This financializes creative output.

- **Incentives for Validators:** Any peer verifying complex lineage computations (like a forked population cross-run) can earn fees (small fractions of royalty) for their compute contribution, funded by a communal pool.

### 4.4 Licensing Framework

Simplifying reuse with built-in licenses:

- **License Genes:** Standard licenses (MIT, CC-BY, CC-BY-NC, etc.) are pre-defined in the `sovereignty` gene schema. Additional clauses (e.g., “non-derivative for 3 gens”) can be parameterized. The system checks these before any `breed` or `compose`, warning users if they would violate terms.

- **Smart Contract Enforcement:** For example, a commercial derivative could require checking with a smart contract that the parent’s license (encoded on-chain) allows it, and to automatically deduct the correct royalty. This is handled by the built-in marketplace API.

- **License Marketplace:** Creators can publish license templates. E.g., a photographer could set a rule “No commercial use unless 15% of revenue to me, no changes” via the UI, which encodes into the seed and enforces via the engine.
